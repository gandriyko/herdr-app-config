## What it does
A frameless full-window overlay: a dim backdrop (a click on it closes the board) and a centered panel that the mod draws (default 82% x 85% of the window, at least 640 x 420 px) with three columns. Drag the bottom-right grip (or the left, right or bottom edge) to resize; the panel stays centered, so its width is twice the pointer's distance from the center. Double-click the grip to reset. The size is saved on mouse up as shares of the window, so it follows the window to another monitor. `mod.open` again, Esc or the close button closes it.

- Needs you: blocked agents and agents asking (finished on a choice menu), oldest first, with a red-tinted card and the pulsing `?`.
- Working: longest running first, with the elapsed time.
- Done: agents that finished while unseen first (newest first, unread check), then seen (idle) agents as normal cards without it, newest first. The column count is the top-level cards in that column (nested children are not counted, a group counts as one).
- Card: the same shape as the sidebar's. Left column: program icon with the status glyph under it (spinner working, pulsing red `?` blocked, a check in a 16 px accent circle for unseen done (the unread mark; seen cards are not dimmed), empty 16 px slot idle, so cards share a minimum height). Line 1: space name (`/ tab` only when the person named the tab and it differs from line 2 and the program name), time on the right. Line 2: the agent's report (else its title, else the tab name if a person named it, else the program name in dim text), wraps up to 2 lines. The PR pill (`#n` and a checks glyph, click opens the PR in the browser) sits in line 1 right after the name, only when there is one, so every card is two lines. When `jira.settings.site` (written by the `jira` mod) is set, an accent pill with a Jira key comes before the PR pill; click opens `<site>/browse/<key>` with `open`. The key is the first one the agent names (title, tab, report) whose project is in `jira.settings.project` (any when none is saved), else its branch's key (`DA-20457-…`). No branch. Line 2 ends with a small reply button. A click on the card (or Enter) closes the board and goes to the agent: `pane.focus` on its terminal, which switches to its space and tab. A sub-agent without a pane first gets one with `terminal.keep` (it lands in its parent's tab, and the core may apply it a moment later), then it is focused; the board waits with two one-shot checks (0.4 s, then 1.6 s after the keep) and stays open with a red line under the header if no pane appears or the keep fails. A sub-agent shown as its own card says "sub-agent of <tab>".
- Agent tree: a sub-agent (a terminal whose `parent` is another listed agent) is drawn under its parent's card, in the parent's column, indented 16 px with a 1 px solid line on the left (nesting up to 3 levels; a parent cycle drops one link). Children are always shown (no folding), so all cards keep the same height. Nested cards are the same cards (click, reply, PR pill) without the "sub-agent of" text. Every agent appears once: a nested agent has no card in its own status column. A group (a top-level card with nested descendants) sits in the column of its most urgent status among itself and all shown descendants (blocked > working > done > idle), so a done parent with a blocked child is in Needs you; each card in it keeps its own glyph and tint, and the reply area opens on the card itself. Within a column a group is ordered by the time of the first member with the group's status that has one, else the parent's (paneless children have none). A child is nested only when its parent's card passes the filters and search; otherwise it is a normal card in its status column. The header summary and space chip counts count agents, not cards.
- Sub-agents without a pane (started with `hc run`) are not in `agents()`, so the board builds them from `terminals()`: every live terminal with a status whose parent chain (depth 8, cycle-safe) reaches a listed agent. They get that agent's space and tab, their own label (`name`, else `template`, else the program) as line 1, line 2 the report or title (else the dim program name, as on any card), no time. Status: `error` = blocked, `done` = idle (it reports to its parent, so its done is never news; same as the agents mod). Asking detection and the reply area work for them. A click keeps the terminal (gives it a pane in its parent's tab) and focuses it; a PR pill appears only if the terminal has a cwd on a feature branch lookup (branch unknown, so normally none). They count in the header summary and space chips like any agent. A kept sub-agent (with a pane) is already in `agents()` and is not doubled.
- Header: summary ("2 need you · 3 working · 1 unseen · 4 seen", zero parts left out, "No agents" when none), search (program, space, tab, report), close.
- Filters: space chips with their agent counts (idle included), and a "PR" segmented control: Any / Has PR / Checks failing / No PR (each segment as wide as its label).
- Keys: up/down between cards (a parent, then its children), left/right between columns (while the search is empty), Enter = go to the selected card, `r` = reply to it (when the search box is not focused; Esc closes the reply area first, then the board).
- Reply: every card has a small reply button at the end of line 2 (tooltip "Reply", also for working agents), or press `r`. The area opens at once with "Loading…" and reads the screen (`hc read <address> --lines 0` (the visible screen only: history reads can scroll the app and take seconds)); it reads again only when that agent's turn or status changes while it is open (no timer; one read at a time, a change meanwhile reads once more; the last good result stays on a failed read, with a red line). Only parsed fields are kept, never the screen text, and they are dropped on close. At its top, in priority order: (1) a choice menu on screen: the menu's heading and description, one full-width button per option ("1  Yes", its description dim below); for Claude's multi-question picker (footer "Enter to select") also the tab bar as small chips (done ones checked) and the question. A click on a simple menu ("Enter to confirm") runs `hc keys <n>`, and after 600 ms, if the same menu is still shown, `hc keys enter`. In the picker a digit only moves the cursor, so a click runs `hc keys <n>`, then `hc keys enter`; after 600 ms the screen is re-read and the area refreshes to the next question/Submit menu, or closes when no menu is left. A "Type something." / "Other" option shows a text input ("Type your answer…", Esc goes back to the buttons): Enter runs `hc keys <n>`, waits 300 ms, `hc send --force <text>`, then follows the screen as above. (2) else the agent's last reply (text after the last `⏺`/`●` line, up to the status line or input-box rule, last 60 lines / 8000 chars). (3) else, for programs without that marker, the screen tail (blank runs collapsed to one, last 30 screen lines). (2) and (3) are monospace 11 px, wrapped at the box width (spaces kept, a line of only rule characters becomes a thin divider; the text between dividers is a selectable `TextView`, so it can be selected and copied with Cmd+C; while the pointer is over the text box the panel's press handlers don't stop the press or close the board, so a drag reaches the selection), up to 240 px high with a scrollbar, scrolled to the bottom after each refresh (requested in render and once more 50 ms later, after layout). Below it a text box, focused: the placeholder is the prompt suggestion, Tab fills it, Enter sends the text (or the suggestion when the box is empty) with `hc send` (a working agent queues it). `hc send` waits while the agent's input line holds a person's unsent draft (Claude's gray suggestion doesn't count), so the send runs through `exec` with a 3 s timeout (a normal send takes under 1 s) and then shows "Not sent: hc send is waiting for an unsent draft…". Errors show as a red-tinted strip with foreground text. Esc closes; a press on another card's reply button closes this area and opens that one at once (the button acts on the press, not the click); a failed send shows the error under the box and keeps the text. Only one reply area is open; closing the board or the card leaving the list closes it.

## Files
- main.js: the view.
- prs.js: gh PR lookups and Jira key helpers (state is kept by the view instance). Copy of `lib/prs.js`; edit it there and run `scripts/sync-lib`.- card.js: card pieces shared with agents-copy (time in state, program icon, status glyph, PR colours, PR filter choices). Copy of `lib/card.js`; edit it there and run `scripts/sync-lib`.
- asking.js: the asking detector and its read queue. Copy of `lib/asking.js`; edit it there and run `scripts/sync-lib`.
- reply.js: pure parsers for the reply area (menu options, input-line suggestion, the agent's question or last reply).
- reply.svg: reply icon.
- grip.svg: resize grip.
- check.svg, x.svg, spinner.svg, search.svg, chevron-down.svg, chevron-right.svg: icons.

## Settings and data
- Shared `agents-board.size` ({ w, h }): shares of the window, each clamped to 0.4-0.98, default { w: 0.82, h: 0.85 }.
- Shared `agents-board.filter` ({ space, pr }). A space that is gone counts as All. Search is not saved.

## Notes
Asking detection: Claude Code reports `blocked` only for tool-permission prompts, so a menu of its own ("Enter to confirm", "Esc to cancel", a `❯ 1.` selector, `(y/n)`) shows as done/idle. Only choice menus count; a reply that merely ends in `?` does not. The footer phrase must start its line or follow a `·`, and a y/n prompt must end its line, so a diff or reply that quotes them (e.g. `("Enter to confirm")`) is not a menu. While the board is open, for each done/idle agent it runs `hc read <address>` (the screen only) and matches the last 14 lines above the input box for a menu. It reads again when the key `(address, turn, status, title)` changes: a new turn, done turning idle (the person looked at it, e.g. after dismissing a menu), or a new terminal title. Such an agent shows as blocked until the next read says otherwise or it works. One read at a time; nothing on a timer; a redraw only when an agent's asking state changes.

Reply suggestion heuristic: `hc read` returns plain text, so Claude's gray suggestion is the text after `❯ ` on the input line between the two `─────` rules near the bottom. A draft typed in the terminal looks the same and shows up as the "suggestion" too. Menu options are found by the menu footer ("Enter to select/confirm", "Esc to cancel"): lines like `❯ 1. Yes` / `  2. Not now` scanned upward over indented description lines, blank lines and rules, up to the question or the tab bar (at least two, numbered from 1). Without a footer, the last 14 non-empty lines above the input box are used. Reads happen only when the area opens and once after a menu key; the screen text is never stored, only the suggestion and options, dropped on close.

Esc closes the reply area, then the board. Column headers are dot, title and count, with no sort hints.

Everything is live from `agents()`, `terminals()`, `spaces()` and `panes()`; the view redraws when they change. A 30 s timer only refreshes the durations and the PR lookup.

PR lookups: each cwd is resolved once to its git common dir (cache capped at 200), so worktrees share one `gh api graphql --cache 55s` call (open PRs, first 100: number, head branch, head commit's check rollup state; 15 s timeout). gh's disk cache is keyed by the request, so agents-copy, with the same prs.js, shares the answer (opening the board doesn't ask GitHub again). An agent that names a Jira key (title, tab, report; only keys of `jira.settings.project` when it is saved) gets the open PR whose branch has that key, even when its folder is on another branch; with no such PR it gets the folder branch's PR only when that branch names no Jira key. One gh call at a time; gh is asked only for feature branches and Jira keys agents name (a repo with keys only, e.g. on its default branch, is asked on the same schedule): the default branch (`git symbolic-ref --quiet --short refs/remotes/origin/HEAD`, re-read every 30 min; without it `main` and `master`), a null branch and a detached HEAD are never asked, and a repo with none of them left gets no gh call. A feature branch not asked about yet is asked at once, then the repo every 5 min while none of them has an open PR, every 60 s while one has (5 min after a failure, keeping the last good answer). When an agent without a PR pill stops working (it may have just opened a PR), its repo is asked at once and once more 60 s later (gh's 55 s cache can hand the first ask the old answer); agents of one repo stopping in the same minute share one recheck. If gh is missing or not logged in, pills disappear and it retries every 10 minutes. At most 30 repos are cached. Agents on other machines have no PR. The view redraws only when the PR map changes. When the dialog closes everything stops.
